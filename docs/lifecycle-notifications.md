# Lifecycle-уведомления

## Cron

`/maintenance/game-requests` должен вызываться **не реже раза в час**: дайджест
«Срочно» считает окна в локальной зоне игрока (12:00–15:00 и 18:00–21:00), и
редкий запуск попадёт в окно только части часовых поясов. На production уже стоит
`*/5 * * * *` в crontab пользователя `matvey`, менять его не нужно.

```bash
curl -fsS -X POST -H "Authorization: Bearer $MAINTENANCE_SECRET" https://<app-host>/maintenance/game-requests
```

### Проверка без отправки

`?dryRun=1` прогоняет отбор аудитории и сборку текстов, но ничего не шлёт и не
пишет в `NotificationDelivery`. В ответе — та же разбивка по статусам плюс до
пяти примеров текста на кампанию. Использовать перед каждой новой кампанией.

```bash
curl -fsS -H "Authorization: Bearer $MAINTENANCE_SECRET" "https://<app-host>/maintenance/game-requests?dryRun=1"
```

Обслуживание игровых заявок в этом режиме пропускается целиком: оно шлёт
транзакционные пуши и меняет статусы, а dry-run обязан быть без последствий.

Повторные вызовы внутри одного окна безопасны: `NotificationDelivery.dedupeKey`
не даст отправить второй пуш за тот же слот. Чтобы частый cron не перебирал всю
базу вхолостую, дайджест сначала группирующим запросом проверяет, открыто ли окно
хоть в одной зоне, и в большинстве прогонов выходит сразу.

## Что уже отправляется

Порядок в `runLifecycleCampaigns` — это приоритет: дневной лимит один на все
кампании, и кто отработал раньше, тот его и занял. Кампании идут строго
последовательно, иначе две успели бы проверить лимит до того, как любая записала
доставку.

| Кампания | Кому | Когда | Проверка перед отправкой | Куда ведёт |
|---|---|---|---|---|
| `onboarding_incomplete` | не закончил анкету | через 2 часа, не дольше 7 дней | форма всегда не пуста | `/onboarding` |
| `likes_waiting` | получил лайк и не вернулся | лайку сутки, игрок сутки не заходил | `getIncomingLikePlayers` не пуст | `/discover?view=likes` |
| `first_players_ready` | закончил анкету, ни одного свайпа | через сутки после регистрации | минимум 3 кандидата | `/discover` |
| `new_players_arrived` | не заходил двое суток | аккаунту больше 3 дней | минимум 2 новых кандидата с последнего визита | `/discover` |
| `training_nudge` | нет активного поиска и запланированной активности | накануне свободного дня из профиля | не нужна — ведёт в форму | `/play/searches/new?sport=…&day=…&time=…` |
| `win_back` | не заходил от 7 до 60 дней | раз в неделю | минимум 3 кандидата | `/discover` |
| `hot_search_digest` | все с уведомлениями о предложениях | 12:00–15:00 и 18:00–21:00 локально | подходящие «срочные» поиски есть | `/discover?view=hot` |

## Правило пустого экрана

Пуш не должен приводить на пустой список — это худший исход, чем молчание.
Поэтому каждая кампания перед отправкой считает контент **тем же запросом,
который рисует экран**: `likes_waiting` вызывает `getIncomingLikePlayers`,
остальные — `summarizeDiscoverCandidates` с тем же `view`, что открывается по
ссылке. Дайджест фильтрует авторов поисков так же, как вкладка «Срочно»
(активный, верифицированный, не в блоке) — иначе он обещал бы игры, которых на
экране нет.

`summarizeDiscoverCandidates` намеренно не идёт через `getDiscoverCandidates`:
тот пишет `DiscoverImpression`, и показы, которых не было, испортили бы разметку
для будущих моделей.

## Переменные окружения

- `MAINTENANCE_SECRET` (или `CRON_SECRET`) — доступ к endpoint'у.
- `LIFECYCLE_CAMPAIGNS_ENABLED` — рубильник всех lifecycle-рассылок,
  по умолчанию **выключен**. Порядок выката: сначала код с выключенным
  рубильником, потом `?dryRun=1` и проверка аудитории и текстов, и только затем
  включение. Cron ходит раз в 5 минут — после деплоя догнать первую рассылку уже
  нельзя. На dry-run рубильник не влияет.
- `LIFECYCLE_HOLDOUT_PERCENT` — доля контрольной группы, 0–50, по умолчанию `0`.
  Игроки из холдаута получают строку `NotificationDelivery` без пуша: это база
  сравнения для retention. Включать имеет смысл, когда достижимая аудитория
  дорастёт до сотен: на десятке устройств холдаут съедает охват и не даёт
  статистики.

## Как добавлять кампании

Новые пуши отправляются только через `sendCampaignPush` из
`src/server/notification-campaigns.ts` — прямой вызов `sendPushToUser` обходит
частотные лимиты, тихие часы и журнал доставок.

1. Добавить запись в `CAMPAIGNS` (категория, кулдаун, тумблер настроек).
2. Вызвать `sendCampaignPush` со стабильным `dedupeKey` вида
   `<campaignKey>:<userId>:<период>`.
3. Целевое действие отметить через `markCampaignConversion`.

Тексты живут в `src/lib/i18n/server/notifications.ts` и приходят на языке игрока
(явный выбор → страна проживания → английский). Для счётных фраз есть
`pluralKeySuffix`: у русского три формы, поэтому ключ выбирается по числу.

Лимиты по умолчанию: 1 lifecycle-пуш в сутки, 3 в неделю, тихие часы 22:00–09:00
по локальному времени игрока. Кампания может поднять свой потолок (`maxPerDay`,
`maxPerWeek`) — так сделано для дайджеста, у которого два слота в день.

## Таймзоны

`User.timezone` проставляется в `PATCH /me` по домашним координатам
(`tz-lookup` по `homeLat`/`homeLng`). Для уже зарегистрированных игроков —
разовый бэкфилл:

```bash
npm run db:backfill-timezones -- --dry-run
npm run db:backfill-timezones
```

Без зоны движок откатывается на `Europe/Moscow`.
